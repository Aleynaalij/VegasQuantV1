## Security and isolation contract

- Production configuration/defaults are unchanged. Feature registry enforcement is combined-only and requires `VQ_STAGE_FEATURE_CONTRACT=vq-stage-features-v1`. Missing flag leaves the previous four-RPC behavior; malformed flag invalidates staging configuration. Missing isolated URL/key/profile/target fails closed, never falls back to production.
- First published branch tree includes `git.deploymentEnabled["codex/atlas-consumer-contracts"]=false`. Exact-head workflow checks out the PR head; both reviewed source branches stay intact. No deployment is requested by this package.
- Optional SQL lives under `scripts/operations`, **not** Supabase production migrations. It requires postgres current/session roles, the installed namespaced synthetic gate, expected fixture migration records and isolated invoker eligibility projections. It rejects outbound extensions/trigger calls, scheduled-worker ambiguity, nonempty storage, realtime publication membership, unsafe readable views, non-postgres table ownership and tables lacking existing RLS.
- Original security-definer function OIDs, owners and grants are preserved with additive stage checks; original definitions are retained for audit. Existing invoker views remain invokers; every public source table retains its original RLS plus a restrictive stage gate. No new caller grant to original tables/functions is made. Original worker grants are preserved, not expanded. Private tables with interactive grants require original RLS; private definer-side writes also receive deferred commit guards. Volatile SQL definers and unexpected function ownership are refused rather than wrapped permissively.
- A separately reviewed pre-install catalog is now REQUIRED. The installer refuses to bless a snapshot it captures itself. The metadata includes definitions, function owner/ACL, relations/views/options/owner/ACL, columns and column ACL/defaults, constraints, triggers and policies. A new unreviewed permissive profile policy after that reviewed artifact is rejected transactionally before feature objects are created. The artifact must come from reviewed original preparation/source dependencies on the specific isolated database, not a blind export accepted as proof of equivalence. OIDs make it target-specific.
- **Known operator-DDL limitation, retained from Elo's independent review:** runtime fingerprints close the manifest and executing guards, but those guards cannot execute through a table whose RLS a privileged operator has disabled. The disposable-fixture counterexample explicitly records a non-owner direct read after `DISABLE ROW LEVEL SECURITY`, alongside manifest NULL. That is NOT a passing direct-data security control. Ordinary users cannot perform the DDL; a malicious/unsafe privileged database operator is outside this enforcement boundary. Hosted/security acceptance remains blocked until the reviewer explicitly accepts the operational DDL/preflight boundary or a separately reviewed independent direct-data boundary is implemented. No green aggregate/manifest result resolves this finding. Existing RLS preflight is retained; no production grants/roles were changed.
- Writes accept only registered columns. No account Auth, role, Dealer-card marker, stake/odds fabrication, storage upload, realtime subscription, billing, provider, schedule or notification-dispatch path is exposed. Existing community `stake` remains subject to original community rules; the adapter creates no betting recommendation or official publication. User-supplied `user_id` must match `auth.uid()`; post photo paths are null-only until storage is separately reviewed.
- POST/UPDATE/DELETE requests use a client-generated request identity and actor advisory transaction lock; natural keys, stable supplied post/comment IDs and original parlay/share dedupe remain authoritative. There is **no blanket exactly-once claim** for repeated human submissions or unrelated RPCs. No automatic retry queue replays a write.
- Existing browser authorization/age/membership checks repeat after reads. Mutation authorization is additionally inside the original database transaction, so a failed final in-transaction check rolls back the change and its trigger effects. An authorization change after commit is not a claim that the preceding authorized transaction never happened.
