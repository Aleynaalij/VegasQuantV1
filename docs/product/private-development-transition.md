## Isolated implementation

1. Use one database-authoritative mode and an allowlist of independently verified Auth UUIDs. Require a matching live MFA session on each protected request while private mode is active. Existing role and access policies remain in force for the allowed owner.
2. Apply explicit, reviewed restrictive policies to protected tables and write paths. Review all executable RPCs and view dependencies, and add the same check before privileged reads or effects in protected definer functions and application routes. Decide the exact signed-out surface before wiring access. The landing, support, privacy, and recovery surfaces need a payload and cache review. For public card routes, preserve authorized owner image rendering without anonymous credentials.
3. Preserve the existing distinction between machine credentials and interactive sessions. Validate every privileged handler before it obtains or uses a service client. Use actual worker identities in protected staging tests. Disable new account creation through the supported Auth configuration in the approved environment. Test that OAuth, password reset, callbacks, invites and account recovery follow the intended boundary even when a session is minted.
4. Handle existing sessions through two separate controls. The database request check denies access before token expiry. The supported Auth session controls handle refresh revocation, and a Realtime disconnect or drain plus Storage URL expiry/cache coverage must be demonstrated separately. A rollback can restore access rules, while revoked sessions require sign-in again.
5. Keep `src/proxy.ts` unmodified during this prototype. The published #293 head `2770a8b08efc2e605b55fe32d4b88579dfd42106` adds its deny-only discovery rollback and keeps the legacy `/?game=` redirect scoped to `/`. Compare exact branch heads before touching the proxy and test both routes on an isolated integration ref if a later draft needs a proxy change. The launch shell must be backed by the server and database policy, including direct URLs, service worker cache and mobile navigation.

The fixture in `tests/sql/fixtures/private-development-access.sql` is a local proof. Run `node --test tests/sql/private-development-access.mjs`. The checks cover the existing policy in open mode, both JWT and live-session MFA, mismatched or revoked sessions, anonymous and unconfirmed identities, allowlist removal, banned accounts, service continuity, control settings and reopening. It also exercises existing entitlements under restrictive RLS, a modeled invoker and definer RPC, object ownership and a publication-backed event table. The same synthetic non-owner claims lose access on enable and regain their existing grants on rollback. Removing the owner's live session denies subsequent protected requests under the unchanged JWT. The service fixture can append an event while disabled users cannot read it. This is a local database test. The storage and publication fixtures evaluate SQL policy decisions. Hosted Auth, REST transport, application policies, signed URL revocation, existing Realtime connections and protected browser navigation require dedicated acceptance.
