## Inactive migration and owner-operated steps

The exact migration in #242 is [20261107173919_platform_tester_research_access.sql](../../supabase/migrations/20261107173919_platform_tester_research_access.sql). Applying it in an authorized environment creates no cohort or active feature. It provides private SQL operations for the database operator. Client and service roles cannot manage grants. The audit records the database session role, a bounded operator reason, operation and before/after state. The reason travels in a private row keyed to the current transaction. Operator calls remove it before returning, and failed calls roll it back. The migration and operations require no custom configuration parameter privileges. Use a change reference or short rationale without account information. Roster audit uses an opaque grant ID. Auth account deletion removes its user mapping and is recorded without the user's auth ID. The database owner's administrative ability to alter or drop schema is outside this control.

1. Use an explicit historical UTC cutoff and the approved Stage 1 features. The final inclusive cutoff is `2026-11-08T04:59:59.999999Z`, equivalent to creation before `2026-11-08T05:00:00Z`. If an initial cohort is approved before that boundary, seal it with a separate batch name and a fixed historical release-time cutoff. After midnight, use a distinct final batch. Carry forward individual revocations before enabling it. After canary acceptance, enable the final batch and clear the initial batch flags in one transaction. A sealed batch cannot be expanded or resealed with a later cutoff. Review aggregate counts for eligible, excluded, already covered and newly covered accounts. Check the migration checksum, live main and policy anchors. Keep both cutoffs out of the migration.
2. In an authorized isolated environment first, call `private.seal_tester_batch(batch_name, approved_cutoff, reason)`. Use bound parameters. The name and cutoff are immutable after seal. The roster snapshot excludes anonymous Auth accounts. Replaying the same cutoff keeps revocations and account removals in place.
3. Call `private.configure_tester_batch(batch_name, approved_features, true, canary_user_id, reason)` for one existing eligible roster account. Read back the state and audit. Run lobby and direct-link checks for a tester, existing paid or historical account, signed-out visitor, and a signed-in account without access. Verify both UI and direct RPC/table behavior, including admin and other users' private records.
4. Only after approval and canary acceptance, call `private.configure_tester_batch(batch_name, approved_features, false, null, reason)` for the reviewed cohort. Use `private.set_tester_revoked(batch_name, user_id, true, reason)` to revoke one grant and the same function with `false` to restore it if approved. Restoring preserves the other live eligibility checks. Release or rollout evidence stays separate from synthetic fixture results.
5. For rollback or the approved app-store transition, call `private.configure_tester_batch(batch_name, array[]::text[], true, null, reason)`. To isolate one feature, configure only the approved remaining features. Verify the next protected request fails for removed tester access, and that paid, historical complimentary and free paths still work. Keep the sealed roster and audit. If the UI must be reverted, disable the grant first and revert the app change separately.
